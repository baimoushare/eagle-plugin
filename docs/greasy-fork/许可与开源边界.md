# Eagle 采集插件：许可与开源边界

## 当前选择

本仓库保持公开，但采用自定义 `All Rights Reserved` 使用许可：

- 源码公开，方便 GitHub、jsDelivr、Greasy Fork 和用户检查；
- 允许个人用户安装和运行；
- 允许个人为本地使用做修改，但不允许公开发布修改版；
- 未经书面授权，不允许镜像、搬运、重新打包、商业再分发或收费服务；
- 不能称为 MIT、Apache、GPL、MPL 等 OSI 开源项目。

完整条款见仓库根目录 `LICENSE` 和 `docs/greasy-fork/脚本使用许可.md`。

## 为什么不选择 MIT

MIT 允许别人：

- 商用；
- 修改；
- 闭源再发布；
- 改名后打包出售；
- 用于其他产品或服务。

只要求保留版权和许可证文本。如果目标是防止搬运、改名转卖或商业再分发，MIT 不符合需求。

## 常见协议对比

### MIT

最宽松，允许商用、修改、闭源和再发布。适合最大化传播，不适合限制商业搬运。

### Apache-2.0

和 MIT 类似，允许商用和闭源衍生；额外提供明确的专利授权、变更说明和 NOTICE 要求。

### MPL-2.0

文件级弱 Copyleft。修改并分发原文件时，原文件通常要继续公开源码；可以与闭源文件组合。比 MIT 更能保护单文件用户脚本的直接修改，但仍允许商业使用。

### GPL-3.0

允许收费和商业使用，但公开分发衍生版本时通常必须继续 GPL 并提供源码。比 MPL 更严格。

### AGPL-3.0

在 GPL 基础上处理网络服务部署场景。当前项目主要是浏览器油猴脚本，AGPL 相比 GPL 通常没有明显额外收益。

### PolyForm、Business Source License、自定义许可

可以限制商业用途、竞争性使用或再分发，但通常不属于 OSI 开源。适合“源码公开但保留商业控制权”的项目。

## 本项目的第三方代码例外

`eagle-x-collector.user.js` 包含上游代码、MIT 标识和第三方来源说明。根目录自定义许可不能覆盖第三方代码，也不能删除上游 MIT 条款。

以后新增第三方依赖时，需要记录：

- 来源项目和作者；
- 来源 URL；
- 许可证类型；
- 涉及文件；
- 是否允许当前分发方式。

## GitHub 设置

仓库保持 Public。根目录使用 `LICENSE` 文件，而不是 GitHub 的 MIT/Apache/GPL 模板。

README 应明确写：

> 本项目为源码公开、非开源项目。使用、修改和再分发权限以仓库根目录 LICENSE 为准。

不要在自定义许可中混入 MIT/GPL 的授权文字，也不要同时标注“MIT License”和“All rights reserved”。两者授权范围冲突。

## 后续改成真正开源时

如果未来决定允许社区合法修改和发布：

- 希望宽松传播：Apache-2.0；
- 希望修改后的原脚本文件继续公开：MPL-2.0；
- 希望公开分发的衍生项目整体继续开源：GPL-3.0。

改许可证前要先核对第三方代码和历史贡献者，因为新许可证只能覆盖你有权授权的原创部分。
